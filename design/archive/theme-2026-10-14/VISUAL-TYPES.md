## Core rule

Choose the visual type from the **concept relationship being taught**. Do not blindly use box-arrow flowcharts. A chapter page may mix visual types when the subject contains different relationships: for example, an overview concept map at the top, a checklist table for tests, and one small decision tree for a genuine nest of yes/no branching.

A flowchart is not a generic “make it visual” container. Use it only when order or process is the teaching point.

### Primary backbone can be more than a map

The **top-of-page backbone** (the one primary navigational / orientation visual) may be any of these when it best matches the concept:

| Backbone | Use when the learner must grasp… | IFRS teaching examples |
|---|---|---|
| **Concept map** | Relationships among peers / residuals / links | Asset ∥ Liability → Equity |
| **Hierarchy stack / tree** | Part–whole or authority layers | Qualitative characteristics; IAS 8 hierarchy |
| **Decision tree** | Diagnostic yes/no branching | Recognition; definition of a lease |
| **Flowchart / process flow** | Mandatory process steps (not mere association) | True procedural sequences only |
| **Timeline** | Events or requirements along **time** (dates, stages, vesting, transition) | Lease term; vesting period; effective date / transition |
| **Formula / equation board** | An identity or computation as the organising idea | Equity = A − L; ECL = PD × LGD × EAD (teaching layer); ROU initial measurement build-up |
| **Statement layout** | How amounts **sit on a primary statement** | Profit or loss structure; OCI; statement of cash flows (operating / investing / financing); financial position groupings |
| **Group / org chart** | Control, ownership, or consolidation **structure** among entities | Parent–subsidiary; NCI; investment entity structures; IFRS 10 control map |
| **Party / role cast** | Who the **actors** are (icons + labels), before or beside process | Customer, supplier, lender, investee, agent vs principal, parent, subsidiary. **Not** “Reporting entity” as a peer cast icon beside Parent/Subsidiary (category error — reporting entity is the **boundary/unit**, taught by dashed group plate; see Consol boundary grammar). |
| **Role-based flowchart** | A process told through **who does / who is affected** (swimlanes or role columns) | Revenue contract parties; lease lessor/lessee; consolidation elimination roles |
| **Matrix / table** | Compare bases, options, or criteria across a spectrum | Measurement bases; classification grids; **IAS 37 liability spectrum** (card-grid exemplar) |
| **Waterfall / build-up** | Cumulative roll-forward or amount build (from here to there) | Equity bridge; P&L build-up; measurement reconciliation — **not** peer definitions |
| **By-phase / lifecycle strip** | Phases of accounting treatment (not calendar time) | Recognise → measure → present / disclose |

**Timeline ≠ flowchart.** A timeline is anchored to calendar or contractual time. A flowchart is a procedure. Do not draw a timeline as a box-arrow “process spine” unless the teaching point is literally a procedure.

**Formula ≠ decorative callout only.** When the formula *is* the logic of the page, make it the backbone (large, labelled terms that link to nested explanations), not a tiny footnote under a generic map.

**Statement layout ≠ reprint of a full set of FS.** Use a **schematic** P&L / OCI / SCF / SFP (labels + grouping + subtotals teaching cues). Hyperlink line-items or brackets to detail sections. Never paste a copyrighted model set verbatim.

## Taxonomy: concept type to visual type

| Concept type | Preferred visual | Avoid when |
|---|---|---|
| **Parallel definitions / peer elements** (for example, Asset ∥ Liability) | **Concept map:** place peers side by side and label links such as “residual of” and “changes in”. | The concepts are peers or co-existing definitions; do not force them into a vertical A→B flowchart. |
| **Hierarchy / part-whole** (for example, fundamental qualitative characteristics then enhancing characteristics; reporting-entity boundaries) | **Hierarchy stack / tree map** or a layered concept map. | There is no parent-child or containment relationship; do not imply chronology. |
| **Process with mandatory order** (steps that must happen in sequence) | **Flowchart / process flow** with explicit order, inputs, outputs, and decision gates where needed. | The content merely has a logical association, comparison, or hierarchy without a required sequence. |
| **Diagnostic yes/no branching** (for example, recognise or not; lease or not) | **Decision tree** with a clear question at each branch and an outcome at each endpoint. | There is no real branch, or the branches are only alternative explanations; do not draw decorative diamonds. |
| **Compare options / bases / criteria** | **Matrix / comparison table** with consistent rows, columns, and selection cues. | The options must occur in sequence or are parts of one whole; do not turn a comparison into a process spine. |
| **Lifecycle / phases of accounting treatment** (for example, recognition → measurement → presentation) | **By-phase graphic / swimlane-light** showing phases, owners or outputs, and useful cross-links. | The arrows suggest a mandatory decision procedure when the point is simply the phases or locations of information. |
| **Calendar / contractual time** (dates, periods, vesting, transition windows) | **Timeline** with labelled milestones; nest detail under each marker. | Time is not the organising idea — do not fake a timeline for a pure definition page. |
| **Identity / build-up computation** | **Formula / equation board** as backbone; each term expands to a nested explanation or checklist. | The formula is only a side note — then keep it as a callout under another backbone. |
| **Where it appears in primary FS** | **Statement layout** (schematic P&L, OCI, SCF, SFP) with teaching brackets / subtotals. | The page is not about statement structure or line-item placement. |
| **Cause ↔ effect / trade-offs** | **Multi-flow / balance diagram** showing reinforcing, opposing, or conditional links. | The relationship is not chronological; do not present a trade-off as a fake sequence. |
| **Checklist / tests inside a definition** | **Numbered checklist table**, often nested under or linked from a concept-map node. | The checks are not sequential steps or do not produce a binary decision; do not inflate every list into a decision tree. |
| **Equation / residual identity** (for example, Equity = Assets − Liabilities) | **Equation callout + concept-map link**, or promote to **formula backbone** when the identity organises the whole chapter. | The equation is not a process step; do not place it as one box in a flowchart. |
| **Group structure / control** (parent, subsidiary, NCI, investee) | **Group / org chart** with labelled links (controls, owns, consolidates, NCI). | The page is only about one entity’s line items with no multi-entity structure. Do not fake a group chart for a pure definition list. |
| **Named parties / roles in a fact pattern** | **Party icons** (entity, customer, supplier, lender, employee, agent, principal, etc.) in a cast row or around a mini-scene. | Icons without labels, or decorative people that do not carry accounting meaning. Always pair icon + role label. |
| **Process where role matters more than bare steps** | **Role-based flowchart** (swimlanes or role columns): each lane is a party; arrows show transfers, rights, or accounting entries between roles. | A pure calculation with no parties — then prefer formula / matrix. A single-entity definition page — then prefer concept map. |
| **FAQ / pitfall contrast** | **Two-column contrast cards** or paired callouts: “What it means” vs “Common trap”, or “Yes” vs “No”. | The content requires a full option matrix, chronology, or branching diagnosis. |

## Composition and mixing rules

- A chapter may combine: one **primary backbone** (map, tree, timeline, formula, statement layout, matrix, by-phase strip, or — only when justified — flowchart / decision tree) + secondary checklists / small decision trees / contrast cards / worked-example grids.
- Use **at most one primary backbone at the top** of a chapter. Secondary visuals belong below or beside the relevant explanation.
- If there is no true **procedure**, the top visual **must not be a flowchart**. If there is no true **calendar/contractual time**, do not force a timeline. If the page is not about **statement structure**, do not force a P&L/SCF skeleton.
- Keep links and labels semantic. A line should say what the relationship is (such as “residual of”, “supports”, “depends on”, “vests over”, or “presents in”), not merely use an arrow as decoration.
- Keep a worked example subordinate to the concept: use a small grid or callout, not a new visual system that competes with the page overview.
- **Mixing is encouraged** when the chapter contains different relationship types (e.g. statement layout backbone + nested decision tree for classification + checklist for measurement).
- **Party icons** are a cast layer, not a substitute for the backbone: place a role cast above a role-based flowchart, or pin icons on a group chart / concept map nodes.
- Prefer a **role-based flowchart** over a generic box spine when the teaching point is *who* transfers/controls/pays — still only when there is a real process; do not invent swimlanes for parallel definitions.
- Prefer a **group chart** when the teaching point is multi-entity structure (IFRS 10 / IFRS 3 / IFRS 12 bridges), not when “entity” only means the reporting entity in the abstract.

## Four-question design check

Before drawing, Design should answer:

1. **What relationship is the learner meant to see?** Peer, hierarchy, procedure, branch, comparison, accounting phase, **calendar time**, cause/effect, test, **formula identity**, **statement placement**, **group structure**, **party roles**, or contrast?
2. **Does order actually matter — and is it procedure or time?** Procedure → flowchart; calendar/contractual time → timeline; neither → do not choose a flowchart or timeline merely because arrows feel “visual”.
3. **Is the organising idea a formula or a statement skeleton?** If yes, consider **formula board** or **statement layout** as the backbone instead of forcing a concept map.
4. **What is the one top-level backbone?** Choose at most one primary backbone, then add only the secondary visuals needed by the local concept.

## Colour and legends (locked 2026-09-27)

Johnny: colour use matters; visuals usually include a **legend**.

### Colour
- Colour must encode a **teaching category**, not decoration.
- Prefer a **small controlled palette** reused across chapters for the same meanings (examples: asset vs liability; fundamental vs enhancing QC; parent vs subsidiary; party roles; inflow vs outflow; see-also / dashed bridge).
- Same meaning → same colour token across the CF pack when practical.
- Do not rainbow every box. If everything is coloured, nothing is taught.

### Colour — meaning gate (Johnny 2026-09-27)
**Only add a colour when it carries a teaching meaning** the legend can state in one plain line. If the only reason is “so the boxes look different,” use shared peer styling (same border/fill) and teach with **position, line style, and labels** instead.

Examples of meanings that earn a colour:
- Resource side vs obligation side vs residual (only if the legend says so and tokens stay consistent site-wide)
- Nested / demoted vs peer → prefer **containment** (not dashed hang); colour only if legend-able
- Matrix column = named category on a spectrum
- Fundamental vs enhancing QC; party roles
- **Consol teaching decode (locked 2026.09.27-6):** Parent solid fill ↔ Unconsolidated FS card fill (“parent alone”); dashed group plate ↔ Consolidated FS card dashed border (“statements about that dashed group”); subsidiaries = outline/empty fill (controlled entities). Colour only with this decode — not decorative rainbow. Same-kind peers still share treatment.

Not enough: three peer cards each painted a different hue with legend “Asset (peer) / Liability (peer) / Equity (peer).”
- Low-fi wireframes may start muted, but once colour is introduced it must stay semantic and consistent (`shared.css` tokens).

### Legends (Johnny 2026-09-27; placement tightened 2026.09.27-4)
- **If you need a legend, use it. If you don’t, don’t.** Prefer **no legend** when the graphic is clear (existing Map grammar lock).
- Need one only when colour, icons, or line styles must be **decoded** and the graphic itself does not already label the meaning (e.g. a matrix spectrum, multi-token map).
- Skip the legend when every node is already named on the graphic (e.g. Ch5 formula board with “Asset / Liability / Equity / Income” on the cards) — a legend then is chrome, not teaching.
- When used: symbol/colour swatch + one plain-language line each; place in a **right-rail** (not a top full-width decode strip); never a design-system essay.

### Matrix / comparison table presentation (Johnny exemplar 2026-09-27)
When the concept is a **spectrum or multi-criteria compare** (e.g. IAS 37 liability spectrum: Nothing → Contingent liability → Provision → Accrual → Trade payable), prefer this card-grid table — not a plain HTML `<table>` dump and not a flowchart.

Locked pattern (from Johnny’s 1.1 provision-spectrum exemplar):
1. **Card grid** — every cell is a rounded rectangle; consistent gutters (cards do not touch).
2. **Strict align** — equal column widths / row heights so the eye reads clean horizontal and vertical lines.
3. **Column = category** on the spectrum (colour token + solid border per defined state).
4. **Row = one test / criterion** (left stub cards, dark label chips).
5. **Spectrum cue** above columns when the axis is certainty / time / strength (Uncertain → Certain).
6. **Line styles in a matrix** (specific to this visual type — different from formula-board):
   - **Solid border** = a defined place on the spectrum (recognised / disclosed / named category).
   - **Dashed border** = absence or N/A (“Nothing”, empty “—” cells) — not wireframe chrome.
7. Short notes / Big 4 chips sit **under** the grid, not inside cells.
8. Legend still required when colour + solid/dashed both appear.

Do **not** force this pattern onto a formula board, concept map, or decision tree. Match visual type to concept (see taxonomy). Ch4 Elements stays an equation board; IAS 37-style spectra use this matrix.
